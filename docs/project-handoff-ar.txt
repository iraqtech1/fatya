3) ما أنجزناه قبل الحجز
- تحويل الباك إند من Node/SQLite إلى Laravel 13.38 وMariaDB؛ البيئة المحلية استُخدمت فيها MariaDB 12.3.3 وPHP 8.4.
- التطبيق والداش مرتبطان بواجهات API مشتركة، مع حفظ المنتجات والإعدادات والعملاء والطلبات والدعم والمخزون.
- جلسات آمنة بكوكيز وتخزين بصمة الجلسة، كلمات مرور Argon2id، تشفير أكواد المخزون، تحقق صلاحيات ومحددات طلبات.
- استيراد XLSX والبحث بالسيريال، واستيراد قاعدة SQLite القديمة عند الحاجة.
- إصلاح مزامنة إعدادات الداش والنسخ القديمة للبيانات وحالة الحساب وإيقافه والصلاحيات.
- إشعارات دائمة لكل عميل، مرتبطة بالطلبات والدعم وتبقى بعد إعادة تشغيل PHP.
- فحص محلي سابق للتسجيل والمنتجات والصور والأسعار والطلبات والدعم والاستيراد والإشعارات.
- نتائج التدقيق ملخصة هنا؛ تعليمات ومتطلبات النشر في DEPLOYMENT.md.

4) ما أنجزناه الآن: المخزون والدفع والتسليم
- إنشاء الطلب يحجز كروت فعلية من المخزون داخل معاملة قاعدة بيانات وبأقفال؛ ليس مجرد إنقاص رقم بالواجهة.
- مدة الحجز الافتراضية 15 دقيقة، مع حد 5 حجوزات فعالة للعميل وحد كمية 20 للطلب.
- نقص الكمية يرفض الطلب كاملاً بدون حجز جزء من الكمية.
- كل كارت له سجل تسليم فريد يمنع تسليمه لطلبين؛ الطلبات المتزامنة تتنافس على المخزون بأمان.
- السعر والكمية والعملة تُثبت وقت الحجز، والحساب المالي بدقة عشرية حتى 3 منازل.
- انتهاء الحجز أو إلغاء طلب غير مدفوع يحرر الكروت ويعيد المتاح للبيع.
- أمر fatya:expire-reservations يحرر المنتهي، ومسجل كل دقيقة في Laravel Scheduler؛ إنشاء طلب جديد ينظف المنتهي أيضاً.
- لا يمكن تسليم الأكواد عبر تغيير حالة الطلب إلى مكتمل من الداش.
- لا يوجد مسار HTTP لمحاكاة الدفع، ولا يُقبل تأكيد دفع من متصفح العميل.
- التسليم يتطلب تأكيداً داخلياً موثوقاً يطابق المرجع والمبلغ والعملة والبوابة والحجز.
- يوجد سجل لإيصالات الدفع ومنع تكرار العملية؛ إعادة إشعار الدفع لا تسلم مرة ثانية.
- الدفع المتأخر بعد الانتهاء أو الإلغاء، واختلاف المبلغ/العملة/البوابة، تذهب للمراجعة ولا تسلم كروت جديدة.
- الكود متاح فقط لصاحب الطلب النشط بعد تأكيد الدفع والتسليم، عبر GET /api/orders/{id}/codes.
- الأكواد لا تظهر في حالة المتجر العامة ولا تُخزن بواسطة ميزة النسخ في localStorage؛ الرد الخاص بالأكواد no-store.
- فك تشفير كل الكروت ينجح أولاً؛ تلف كود واحد يرجع المعاملة كلها بدون تسليم جزئي.
- زر نسخ الأكواد مربوط بالباك إند، ونص إيصال الطلب يوضح حالة الحجز/الدفع. لم نغير CSS أو شكل الواجهة.
- الطلبات التجريبية القديمة لا تُحوّل تلقائياً إلى دفعات مؤكدة ولا تمنح أكواد.

5) المحاكاة المحلية فقط
الأمر: php artisan fatya:simulate-payment ORDER_ID --amount=AMOUNT --provider=Qi --currency=IQD --transaction=UNIQUE_TXN --event=UNIQUE_EVENT
يعمل فقط من CLI في APP_ENV=local أو testing ومع ALLOW_PAYMENT_SIMULATION=true.
القيمة الافتراضية false؛ أبقها false في الإنتاج. لا تستخدم المحاكاة لإثبات دفع حقيقي.
الاختبارات تفعّلها داخل بيئتها المعزولة فقط. البوابة الحقيقية وwebhook الموثق لم يُربطا بعد.
لا توجد حالياً معالجة استرداد مالي تلقائي؛ الحالات غير المطابقة تحتاج مراجعة.

8) التشغيل من جهاز الشركة
جهّز Git وNode.js 22.13 أو أحدث وComposer 2 وPHP متوافقاً مع Laravel 13 وقاعدة MariaDB مناسبة.
استخدم PHP 8.4 كما في دليل الشركة، وتأكد أن PATH لا يشير إلى PHP 8.2 قديم.
على جهاز جديد: git clone https://github.com/iraqtech1/fatya.git ثم cd fatya. على نسخة موجودة: راجع التعديلات المحلية أولاً ثم git pull origin main. لا تحتاج تفك الأرشيف فوق آخر clone.
من جذر المشروع: npm ci
من backend: composer install
انسخ backend/.env.example إلى backend/.env واضبط بيانات قاعدة جديدة محلية وADMIN_PASSWORD خاصاً بك.
من backend وعلى قاعدة جديدة فقط: php artisan key:generate ثم php artisan migrate ثم php artisan fatya:seed.
لا تستخدم migrate:fresh على قاعدة العمل؛ يمسح البيانات. ولا تنفذ seed قبل استيراد قاعدة قديمة.
من جذر المشروع في PowerShell، إذا PHP المطلوب ليس على PATH:
$env:PHP_BIN='C:\path\to\php.exe'
npm run dev
التطبيق: http://127.0.0.1:5173/
الداش: http://127.0.0.1:5173/#/admin
الـAPI: http://127.0.0.1:3001/api/health
هذه روابط محلية تعمل فقط عند تشغيل الخدمات. بيانات دخول الداش من .env؛ الاسم الافتراضي masal، ولا يوجد باسورد سري محفوظ بهذا الملف.
قاعدة العمل غير مضمنة في Git. اضبط اسم القاعدة والمنفذ حسب جهاز الشركة.
نقل نفس البيانات يحتاج نسخة MariaDB آمنة ومعها APP_KEY الأصلي لأن المخزون مشفر؛ توليد مفتاح جديد لا يفك أكواد القاعدة القديمة.
لا ترسل .env أو مفاتيح التشفير أو قاعدة بيانات فعلية داخل GitHub أو محادثة عامة.
إذا لم تنقل البيانات ابدأ بقاعدة جديدة واستخدم كروت اختبار وهمية فقط.
لتنظيف الحجوزات محلياً شغّل من backend: php artisan schedule:work أثناء التجربة.

9) إعادة الفحوصات من الشركة
من جذر المشروع: npm run check ثم npm test ثم npm run build:host.
جهّز قاعدة اختبارات منفصلة ينتهي اسمها بـ _test ولا تحتوي بيانات عمل.
PowerShell من جذر المشروع:
$env:PHP_BIN='C:\path\to\php.exe'
$env:FATYA_TEST_DATABASE='fatya_contract_test'
npm run test:api
الفحوصات تعيد إنشاء بيانات قاعدة الاختبار؛ لا تستخدم قاعدة العملاء أو fatya_dev.
إعدادات اتصال الاختبار تُقرأ من backend/.env، ويمكن تجاوزها بمتغيرات FATYA_TEST_DB_HOST/PORT/USERNAME/PASSWORD.
من backend: composer validate --strict --no-check-publish
php vendor/bin/pint --test --no-interaction
php artisan test --no-ansi

10) الباقي حسب الأولوية
أولاً: سحب main من جهاز الشركة وتجهيز البيئة وقاعدة البيانات واختبار التدفق محلياً. الرفع وCI لتعديلات الحجز مكتملان وناجحان. عند تحديث قاعدة موجودة، خذ نسخة احتياطية واحتفظ بـ APP_KEY ثم نفذ composer install وphp artisan migrate من backend؛ لا تستخدم migrate:fresh.
ثانياً: عند وصول بيانات الدفع، تنفيذ محوّل بوابة موثّق للدفعات الناجحة فقط مع التوقيع وحماية إعادة الإرسال ومطابقة المبلغ والعملة والمرجع، وربطه بخدمة التسليم الحالية.
ثالثاً: تحديد مسار مراجعة المدفوعات المتأخرة/الخاطئة والاسترداد والتسوية المالية قبل البيع الفعلي.
رابعاً: ربط إرسال OTP الفعلي ومورّدي API إذا كانت خدماتهم مطلوبة؛ لا تعتبر المحاكاة إرسالاً حقيقياً.
خامساً: تجهيز الاستضافة والـCron والنسخ الاحتياطي واختبار الاستعادة والسجلات وHTTPS قبل النشر التجريبي ثم الإنتاج.
فحص cPanel السابق أظهر PHP 8.3 وMariaDB 10.3.39؛ نحتاج معالجة قدم MariaDB، والتأكد من SSH/Shell وComposer وصلاحية document root إلى public. لا نفترض أن إعدادات الشركة لم تتغير.
GitHub Pages معاينة ثابتة وليست بيئة تشغيل Laravel/MariaDB.
لم نرفع إلى cPanel ولم نربط دفعاً فعلياً.
